# 任务与协作流程

主干记录团队已接受事实，分支记录候选修改，Issue 用于讨论。任务与所有权只记录一次；当前任务集合的位置从 resources.tasks 解析，不在 Agent 规则里固定。

首次接入 T011 按用户明确授权执行单次 bootstrap，详见 migration-decision。T002/T004 的既有实现是待评审候选，不因导入任务表就变成已认领或已合入；后续任务仍遵守正常流程。

## 状态

planned → ready → claimed → in_progress → in_review → integrated → demo_verified。

planned 表示待绑定、待契约或待命令；ready 表示执行前置条件具备；claimed 表示认领已接受；in_progress 表示正在实现；in_review 有完成项与真实验证；integrated 有实际合并证据；demo_verified 有真实端到端证据，通常只用于最终验收任务。

in_progress 可转 blocked 或 handoff，补齐恢复条件后回 in_progress。评审要求修改可回 in_progress。撤回认领回 ready 时清空执行身份并保留原因。每次变化追加 history，不覆盖历史。已完成任务的新修改另开修复任务。

## 一次任务

确认角色 → 同步并核对实际基线、资源绑定与环境 → 读任务及依赖 → 用独立元数据分支提交认领 → 主干接受 → 用独立任务分支实现 → 用现有 command_ref 验证 → 更新检查点 → PR 评审 → 合入 → 记录实际集成证据。

具体执行 git_workflow 资源。未完成工作可 push 到自己的任务分支并保持 Draft；禁止在共享分支直接开发或推送。一个角色的大模块拆成可独立验收的小任务，完成的小任务可以先合入，不必等整个模块最终完成。

任务 scope 引用模块或资源 ID，不写死业务目录。命令按清单和既有环境解析；没有接入就记 not_run。新任务、范围扩大、重新指派和验收条件变化先单独接受，不随实现偷改。

## 并行和交接

一任务一位执行者、一条可追溯分支、一个主实现 PR。每个 Agent 用独立工作目录。不同逻辑任务若解析到重叠写资源就不得并行；最具体的 accepted 子资源归属优先。

认领以主干接受为准；仓库需要分支最新或串行合并队列，以免两个旧 base 上的认领均通过。CI 与主干保护未接入时，只能说流程约定有效，不能声称系统拥有分布式锁。

原执行者停止写入，保存提交及记录后，维护者接受 owner/session 转移。无法联系旧会话由维护者明确撤销，不按超时自动抢占。看见他人未提交改动不得清理、覆盖或重置。

长任务每 30 分钟保存有效检查点；验证、阻塞或离开前及时更新。失败保留确切原因和尝试，不无限重试；回退优先 revert，处理冲突后重跑受影响检查。未授权的不可逆外部操作先提交具体方案供决策。
