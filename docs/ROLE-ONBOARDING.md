# Agent 首次进入与角色确认

目标流程：读取公共规则 → 确认当前使用者的角色 → 解析实际资源与任务 → 核对环境 → 使用独立分支开始工作。角色确认不等于平台账号授权，规则清晰不等于已启用自动拦截。

## 确认本次角色

1. 用户已明确“我是 B”或已分配本次角色，直接使用该信息，不再次追问同一问题。当前会话换角色时明确记录变化。
2. 已接受的身份映射能唯一识别角色时，向用户说明识别结果并沿用已授权的任务；一人多角色时确认本次任务使用哪个角色。
3. 没有明确角色时，只需询问一次：“你本次负责 A 协议采集、B 预览展示、C 画布应用、D 运行时 API，还是 E 资产集成路演？”不按机器用户名、Git 显示姓名、模型名称或目录名称猜测。
4. 用户选择与仓库已有负责人/分配记录冲突时，说明冲突并按原分配流程处理。映射为空时保存本次使用者的明确选择及来源，由任务接受流程确认；不把空配置解释为已具有所有模块权限。

A–E 是当前团队配置，职责从角色清单和 ownership 资源读取。这里的文字选项仅为当前团队展示；后续新增角色应同步配置及相关 Schema，不假称当前枚举已支持任意角色。

## 写入前形成工作摘要

向使用者简要说明：本次角色与确认来源、任务 ID、负责的逻辑模块、已确认的实际可写资源、需要其他 Owner 配合的边界、当前分支/基线和检查项。

任务记录保存 role_confirmation：confirmed_by、confirmed_at、source 和 reference。真实身份、会话和 owner_role 与任务分配一致；它是确认来源的记录，不是凭此获得 GitHub 权限的凭证。

若角色已经确认、任务已接受且实际范围清晰，不要求用户逐个文件重复批准。新任务或换会话可复用仍有效的已接受角色分配，并记录当前会话；角色/归属有冲突时仅阻塞受影响写入。

## B 的边界示例

本次角色 B，任务是预览超时处理。可修改当前映射中的预览实现及本任务记录；需要 D 装配外层路由时提出明确接口需求，需要 C 接入页面时交付组件契约，不自行改动另一个角色的资源。现有环境文件保持不变。

实际位置没有接受或已失效时，先发现并确认相关资源，不能凭参考目录图创建一套重复代码。没有实际代码的模板阶段可继续做职责、契约与任务准备，但不能声称业务写入边界已落地。
