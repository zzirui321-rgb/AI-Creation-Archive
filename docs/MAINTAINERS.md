# 接入当前 GitHub 仓库

当前仓库为 AiCA-Team/AiCA，Alvintxh 已确认角色 A。现有工程与环境已绑定；其他成员身份、候选资源的 Owner 接受、远端 CI 和保护设置待落实。迁移范围与叠加 PR 顺序见 [迁移决定](COOP-MIGRATION.md)。不另建仓库或替换环境。

## 一次性接入

1. 合并公共规范，更新入口清单的 resources；保留原有项目结构和环境文件，不按模板重排代码。
2. 填真实角色身份，用当前仓库证据发现并确认 bindings。模块/资源使用稳定 ID，实际相对位置只维护一处。
3. environment 引用已有规范和受保护资源；commands 引用已有检查，不新增运行依赖。
4. 从 accepted bindings 生成或更新 CODEOWNERS 与范围检查。嵌套资源由具体归属覆盖父归属；生成结果不是第二份手工事实来源。
5. 沿用现有 CI 接入 validation-contract 定义的检查，实际运行后再设 required checks。不预设 workflow 名、runner、解释器或安装命令。
6. 主干启用 PR、非作者批准、相关 Code Owner 评审、新提交重审、讨论解决、禁止强推/删除，以及分支最新要求或串行合并。实际功能可用性按仓库权限和套餐确认。

## 模板边界

提供规范、数据模板和本地结构检查，不自动修改 GitHub 设置。规则文件无法强迫所有客户端加载，也不是恶意代码隔离。CI 检查器/workflow 本身被修改时必须审核；行为规则、自动检查、仓库权限需配合实施。

公开前由仓库所有者决定代码、协议、素材和私有 Graph 的许可边界；模板不替整个产品选择 LICENSE，也不重新分发原附件。

## 演练

不同工具的两位 Agent 从新 clone 开始：加载同一规范；发现当前结构而不是创建假定目录；核对嵌套资源边界；拒绝重复认领与越权写入；不动环境；中断后从同一任务接手；完成真实端到端 Demo。记录恢复用时和缺口，再精简规范。

## 分支规范接入

沿用当前仓库的分支规则，确认实际 remote、集成目标与共享分支，并更新清单 branch_policy。禁止共享分支直接推送的规范需要 GitHub 保护/ruleset 落实；不要仅提交 Markdown 就宣称已强制生效。认领元数据同样走独立分支。角色确认与 GitHub 写权限分别核实。
